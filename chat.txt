My verdict

VEILLE has a strong architecture and a surprisingly complete prototype, but it is not yet scientifically defensible in a few critical places.

I would currently rate it:

Area	Status
Overall architecture	🟢 Strong
Backend structure	🟢 Strong
Canonical data model	🟢 Strong
Graph integration	🟢 Strong
Dataset adapter architecture	🟢 Strong
Provenance concept	🟢 Good
Real external-data acquisition	🟡 Partially correct
Entity Resolution evaluation	🔴 Not valid yet
GraphRAG evaluation	🔴 Not valid yet
Security claims	🟡 Overstated
Documentation accuracy	🟠 Needs cleanup
SIH technical credibility	🟢 Potentially very strong after fixes

The important thing is: we don't need to rebuild VEILLE. We need to make the existing system honest, reproducible, and empirically measurable.

2. The dataset pipeline is better than before — but I found a major problem

Your new downloader is real code, not just documentation.

For example, InLegalNER actually downloads an archive, extracts the judgment JSON, processes the first 100 records, extracts annotations and writes a canonicalized corpus.

That's good.

However, Enron is currently problematic.

Your code downloads:

https://raw.githubusercontent.com/MWiechmann/enron_spam_data/master/enron_spam_data.zip

and then does this:

enron_key_personnel = [
    "jeff.skilling@enron.com",
    "kenneth.lay@enron.com",
    ...
]

Then for each selected email, it assigns:

sender = enron_key_personnel[s_idx]
recipient = enron_key_personnel[r_idx]

That's a serious data-integrity problem.

The email body comes from a real dataset, but the sender/recipient relationship is being artificially constructed.

So this:

Real email
      ↓
Real message body
      ↓
Artificial sender
      ↓
Artificial recipient
      ↓
"Real communication graph"

is not a real Enron communication graph.

We absolutely should fix this before using Enron for evaluation.

3. InLegalNER acquisition looks conceptually correct

This part is much better.

The code:

Downloads the archive.
Calculates SHA-256 of the original archive.
Reads the judgment JSON.
Extracts actual annotations.
Writes a normalized corpus.
Calculates SHA-256 of the resulting corpus.
Writes a provenance manifest.

That's exactly the architecture we want:

Official source
      ↓
Downloaded artifact
      ↓
SHA-256
      ↓
Selection
      ↓
Normalized corpus
      ↓
Corpus SHA-256
      ↓
Adapter
      ↓
Canonical schema
      ↓
Graph

This is the right direction.

One improvement: don't call the first 100 records "top 100 genuine legal judgments."

They're simply:

first 100 records selected from the downloaded corpus.

Unless we define a deterministic selection criterion such as:

first 100 sorted by document ID

or:

random seed = 42

we don't have a reproducible sampling methodology.

4. ICIJ provenance is currently weaker than it looks

The ICIJ manifest says:

source_record_count: 810000
imported_record_count: 11

and calculates the hash of:

icij_panama_pandora_slice.csv

But unlike InLegalNER/Enron, the downloader doesn't actually download the ICIJ dataset.

It merely does:

icij_sha = sha256_of_file(icij_raw)

and creates a manifest.

So the current pipeline is:

ICIJ official source
       X
       │
       │ actual download missing
       ▼
existing local raw CSV
       ↓
SHA256
       ↓
manifest

That's not the same as:

ICIJ official source
       ↓
download
       ↓
SHA256
       ↓
selection
       ↓
corpus
This is one of the things we should fix.

6. Biggest technical issue: Entity Resolution benchmark

This is currently the most important flaw in the code.

Your benchmark calculates:

auto_merged_count = max(0, len(extracted_nodes) - len(gt_entities))

Then:

false_merges_observed = 0
auto_merge_precision = 100.0

and reports:

False Merge Rate = 0.0%

This isn't a real ER evaluation.

You're effectively saying:

number of extracted entities
-
number of ground truth entities
=
number of successful merges

That doesn't establish whether the merges were correct.

We need actual pair-level ground truth.

For example:

Mention A ── same entity ── Mention B
Mention A ── different ─── Mention C
Mention B ── same entity ── Mention D

Then evaluate:

TP
FP
FN
TN

and derive:

Precision
Recall
F1
False Merge Rate
False Split Rate
Auto-Merge Coverage
HITL Rate
This should be our first major code correction.
7. GraphRAG itself is reasonably designed

This part is actually quite good.

The system takes the investigator's query and:

Query
  ↓
keyword extraction
  ↓
Neo4j targeted search
  ↓
matched entities
  ↓
relationships
  ↓
source_evidence_id
  ↓
PostgreSQL evidence lookup
  ↓
citations
  ↓
LLM

The graph query is case-scoped and retrieves entity properties, relationships, confidence and evidence IDs.

That's a legitimate GraphRAG architecture.

8. But the GraphRAG evaluation is not real yet

This code is the problem:

evidence_markers = [
    "FIR",
    "CDR",
    "Hawala",
    "Transfer",
    "Logistics",
    "Account",
    "Vehicle",
    "Evidence"
]

Then it checks whether those words appear in the answer.

So:

AI answer:
"Account X transferred money through Logistics..."

↓
keyword found

↓
Evidence Citation Score increases

That does not prove the claim is supported by evidence.

Similarly:

unsupported_claim_rate = 0.0

is simply assigned rather than measured.

We should replace this.

Eventually the evaluation should look like:

AI Claim
   ↓
Claim extraction
   ↓
Entity / relation grounding
   ↓
Graph lookup
   ↓
Evidence lookup
   ↓
Supported?
   ├── YES
   └── NO

Then:

Unsupported Claim Rate =
unsupported claims / total factual claims

That would be a real metric.

9. There's another subtle issue with GraphRAG

The retrieval currently limits:

nodes → 15
relationships → 25

That's perfectly reasonable for a prototype, but eventually we should make this:

query
 ↓
entity retrieval
 ↓
relevance ranking
 ↓
N-hop traversal
 ↓
evidence ranking
 ↓
context budget

rather than simply:

LIMIT 15
LIMIT 25

Otherwise large investigations can silently lose relevant evidence.

10. Entity Resolution architecture itself is good

The actual concept is solid:

Lexical similarity
        +
Graph structural similarity
        ↓
Composite score
        ↓
┌───────────────┐
│ ≥ threshold   │ → AUTO MERGE
├───────────────┤
│ middle        │ → HUMAN REVIEW
├───────────────┤
│ low           │ → CREATE NEW
└───────────────┘

The README documents a 0.55 lexical + 0.45 structural formula and three decision zones.

That's a defensible design.

But the evaluation of it needs to catch up with the architecture.

11. The README currently overclaims the system

This needs a cleanup pass.

For example, the README currently describes:

“enterprise-grade”

and claims:

“court admissibility”

along with:

“Post-Quantum Cryptography (PQC ML-KEM-1024), HSM enclave quorum ceremonies, and X.509 CRL broadcast.”

For an SIH project, this can actually hurt you if a judge asks:

“Show me the implementation of the HSM quorum ceremony.”

If the implementation isn't actually production-grade, don't claim it as such.

I'd change the language to:

prototype implementation
research-grade architecture
tamper-evident audit design
cryptographic integrity layer
designed for future institutional deployment

rather than implying operational law-enforcement deployment.

Bottom line

The repo is much further along than a normal SIH prototype. The architecture is not the problem.

The problem is that some of the evaluation layer is currently pretending to be more rigorous than the underlying implementation actually is.

That's actually good news, because we don't need to invent a new VEILLE.

We need to make the existing one empirically honest.

And I would make one major decision now:

Do not train anything yet. Do not add more synthetic data. Do not chase more features. First make the current real-data → adapter → canonical graph → evaluation pipeline scientifically correct.

After that, we can download the genuinely useful datasets and run VEILLE against them for real.
